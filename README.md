# SQL Practice (v0.010.3)

Тренажёр по SQL для подготовки к экзамену School 21 (SQL Bootcamp). Запросы выполняются прямо в браузере на настоящем PostgreSQL (PGlite, WebAssembly): ничего ставить не нужно, всё работает как статический сайт на GitHub Pages.

## Что внутри

116 заданий в 18 разделах. Каждое задание: условие, теория, три подсказки по нарастающей, эталонное решение (с комментариями и без) и автопроверка.

| Раздел | Что в нём |
| --- | --- |
| Day 00–02 | SELECT, множества, JOIN, подзапросы, CTE |
| Day 03 | DML: INSERT, UPDATE, DELETE |
| Day 04 | VIEW и MATERIALIZED VIEW |
| Day 05 | индексы и `EXPLAIN` |
| Day 06 | DDL + DML: новая возможность в модели данных |
| Day 07 | GROUP BY, HAVING, агрегатные функции |
| Day 08 | транзакции и уровни изоляции (ручные задания на две сессии) |
| Day 09 | функции, процедуры, триггеры |
| Team 00 | командный проект «задача коммивояжёра» (граф создаётся в самом задании) |
| Team 01 | командный проект «хранилище данных» (DWH) |

Командные проекты рассчитаны на двоих: в каждом есть старт, **две роли** со своей теорией и заданиями и общая сборка. Роль выбираешь в левом списке.

## Что умеет интерфейс

- Условие, теория, подсказки и решение открываются во вкладках. Левую часть можно **разделить на две панели** (кнопка «⬒» над вкладками): например, смотреть условие и теорию одновременно. В каждой панели свои вкладки.
- Справа редактор запроса (запуск по Ctrl+Enter), кнопка «Проверить», вкладки «Вывод» и «Схема БД» (граф таблиц с PK/FK, содержимое таблицы по клику).
- Слова из теории (`LEFT JOIN`, `COALESCE` и т. п.) кликабельны: открывается окно с объяснением, мини-таблицами, запросом и результатом. Есть и кнопки «Показать пример».
- «📖 Энциклопедия SQL»: 10 статей с живыми примерами, диаграммами JOIN и поиском.
- Темы оформления, размер текста, прогресс решённых заданий хранятся в браузере.

## О чём следует знать

**Данные.** Основной набор данных (`pizza`, модель из школы) воспроизводит учебную базу. Для некоторых заданий нужны свои данные: `demo` (мини-таблицы для примеров), `dwh` (хранилище данных). В Team 00 граф городов создают запросы самого задания.

**Данные для Team 01 придуманы.** Папки Materials с настоящим скриптом базы у нас не было, поэтому набор `dwh` написан по описанию из задания (таблицы, примеры значений, аномалии). Когда будет настоящий скрипт, его нужно подставить вместо `data/dwh.sql`, после чего подогнать примеры в README заданий.

**Скрытый набор данных.** Каждое решение проверяется дважды: на основных данных и на скрытых (основные + добавки из `data/*_alt*.sql`). Поэтому ответ нельзя вписать готовыми значениями через `VALUES`: на скрытых данных он разойдётся с эталоном. В задачах, где в основных данных результат пустой или слишком мал, скрытый набор добавляет строки.

**Числа сравниваются как строки.** `1` и `1.0` для проверки разные значения. Где это важно, в условии написано, как оформить результат (например, `ROUND(..., 2)` или «пиши именно `1`»).

**Порядок строк.** Если в условии есть сортировка, порядок проверяется. Для одинаковых ключей в условии добавлены дополнительные ключи, чтобы порядок был однозначным. Сортировка текста зависит от настроек базы: на сервере школы она может отличаться от PGlite.

**Транзакции.** Каждый запрос выполняется внутри транзакции, которая всегда откатывается: `DROP` и `DELETE` ничего не ломают. `COMMIT`, `ROLLBACK` и `BEGIN` в редакторе запрещены — иначе откат перестал бы работать. Задания на DDL, индексы, триггеры и транзакции проверяются не по выводу запроса, а по состоянию базы после решения (системные каталоги, `EXPLAIN`, тестовые вставки).

**Ручные задания.** Карточки ролей, стартовые страницы командных проектов и все задания Day 08 (транзакции и уровни изоляции, две сессии `psql`) не проверяются автоматически: это инструкция.

**Ограничения.** Проверка похожа на экзаменационную, но не идентична ей: на настоящей защите проверяют люди. Часть заданий допускает несколько верных решений, поэтому в проверках есть «другие верные способы», но экзотический вариант, которого мы не предусмотрели, может быть отвергнут. Если решение верное, а тренажёр спорит, сверь результат вручную и пришли пример.

## Запуск на своём компьютере

```
cd sql-trainer
python3 -m http.server 8000
```

Открой http://localhost:8000. Двойным кликом по `index.html` страница не заработает: браузер не даёт читать `tasks.json` и грузить WebAssembly с `file://`.

Нужен интернет: PGlite подгружается с CDN (jsDelivr, запасной источник esm.sh), шрифты с Google Fonts. Первый запуск скачивает несколько МБ, дальше браузер берёт их из кэша.

Справа внизу две вкладки: «Вывод» и «Схема БД» (граф таблиц с PK/FK и содержимое любой таблицы по клику).

В левом меню кнопка «📖 Энциклопедия SQL»: 10 статей с живыми примерами и диаграммами JOIN, есть поиск. В теории заданий тоже есть кнопки «Показать пример».

Как добавлять задания — см. раздел «Как добавить задание» ниже.

## Проверка, что движок работает

Открой http://localhost:8000/?selftest. Страница прогонит в браузере все эталоны и все «неверные» решения (кроме ручных заданий). В заголовке вкладки появится `SELFTEST OK` и список галочек. Если вместо этого `SELFTEST FAIL`, открой консоль браузера (F12) и пришли текст ошибки.

## Выкладка на GitHub Pages

1. Залей папку проекта в репозиторий (вместе с `tasks.json`).
2. Settings → Pages → Build and deployment → Deploy from a branch → `main`, папка `/ (root)`.
3. Через минуту страница будет по адресу `https://<ник>.github.io/<репозиторий>/`.

## Как проверяется решение

Запрос ученика и эталонное решение выполняются на двух наборах данных: основном (`data/<имя>.sql`) и скрытом (`data/<имя>_alt.sql` и `data/<имя>_alt_*.sql` добавляют строки поверх основного). Сравниваются названия столбцов, строки (с учётом дубликатов) и порядок строк, если в `meta.json` стоит `"ordered": true`. Благодаря скрытому набору нельзя пройти задание, вписав готовый ответ через `VALUES`. Запреты из условия (`DISTINCT`, `JOIN` и т. п.) проверяются по тексту запроса без комментариев и строк.

Запрос выполняется внутри транзакции, которая всегда откатывается, поэтому `DROP` и `DELETE` ничего не ломают.

## Как устроен проект

```
index.html              страница
css/, js/               интерфейс (app.js), схема БД (schema.js), движок БД (engine.js), проверка (checker.js)
vendor/marked.esm.js    разбор Markdown
data/                   наборы данных: <имя>.sql, <имя>_alt*.sql (скрытые), <имя>_schema.md
tasks/<раздел>/exNN_name/  задания (исходники); раздел: dayNN или teamNN<буква>_...
tasks.json              собранные задания; страница читает именно его
tools/build.mjs         собирает tasks.json из папок
tools/validate.mjs      проверяет сами задания на настоящем PostgreSQL
```

## Как добавить задание

1. Создай папку `tasks/day01/ex03_название/` (и `day.json` с названием раздела, если раздел новый) с файлами: `README.md` (условие), `theory.md`, `hints.md` (каждая подсказка начинается с `## Заголовок`), `solution.sql`, `solution_commented.sql`, `meta.json`.
2. В `meta.json`: `title`, `dataset`, `ordered`, `forbidden` и `required` (списки слов), `positive` (другие верные решения, которые должны проходить) и `negative` (типичные ошибки, которые должны отклоняться), у каждого пример есть `why` и `sql`. Если названия столбцов не важны, добавь `"checkColumns": false`. Для заданий с подготовкой и проверкой состояния базы есть `setup` (SQL перед запросом ученика), `verify` (SELECT после решения, его результат сравнивается) и `manual: true` (задание без автопроверки). Дополнительно: `forbidDirectIds` (запрещает записывать указанные столбцы числом в `INSERT ... VALUES/SELECT`), `forbidSetvalLiteral` (запрещает числовое значение в `SETVAL`) и `planContains` (для заданий с `EXPLAIN`: проверяет, что в плане запроса ученика есть указанная строка).
3. Запусти `node tools/build.mjs` и закоммить обновлённый `tasks.json`.
4. Проверь задания на настоящей базе (нужны `psql` и пустая база):

```
createdb trainer_test
PGDATABASE=trainer_test node tools/validate.mjs --verbose
```

Валидатор убеждается, что эталон и все `positive` проходят, а все `negative` отклоняются.

## Что проверено, а что нет

Проверено на PostgreSQL 17.5 (PGlite 0.3.16): все эталоны, все `positive` и `negative`, проверка и сообщения об ошибках; интерфейс в Chromium (дерево, вкладки, подсказки по одной, запуск по Ctrl+Enter, вердикты, прогресс и тема после перезагрузки).

Не проверено: загрузка самого PGlite с CDN в реальном браузере (в среде, где собирался проект, CDN и npm закрыты, поэтому в тесте движок подменялся локальным PostgreSQL). Для этого и нужен `?selftest`. Отличия PGlite от PostgreSQL 17.5 для этих заданий не ожидаются, но порядок сортировки строк в разных регистрах может отличаться от сервера школы.
