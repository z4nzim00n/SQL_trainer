# 11. Транзакции, ACID и теория баз данных

Эта статья — про понятия, которые спрашивают на теоретической части: транзакции, ACID, CAP, нормальные формы, ER-модель и отличие реляционных баз от NoSQL.

## Транзакция

Транзакция — это набор команд, который выполняется **как одно целое**: либо все команды применяются, либо ни одна.

```sql
BEGIN;
UPDATE menu SET price = price + 10 WHERE pizzeria_id = 1;
DELETE FROM menu WHERE price > 2000;
COMMIT;      -- применить всё
-- ROLLBACK; -- или отменить всё
```

- `BEGIN` начинает транзакцию;
- `COMMIT` фиксирует изменения;
- `ROLLBACK` отменяет всё, что сделано после `BEGIN`;
- `SAVEPOINT имя` и `ROLLBACK TO имя` позволяют откатить часть транзакции.

Пока транзакция не зафиксирована, другие сессии её изменений обычно не видят.

## ACID

Четыре гарантии надёжной транзакции:

| Свойство | Что гарантирует |
| --- | --- |
| **Atomicity** (атомарность) | «Всё или ничего»: при сбое посередине не останется половины изменений |
| **Consistency** (согласованность) | Транзакция переводит базу из одного корректного состояния в другое, не нарушая ограничений |
| **Isolation** (изоляция) | Параллельные транзакции не мешают друг другу так, как будто выполняются по очереди |
| **Durability** (надёжность) | После `COMMIT` изменения сохранятся даже при падении сервера |

Именно **Durability** отвечает за то, что успешно завершённая транзакция не пропадёт при сбое.

## Уровни изоляции

Чем выше уровень, тем меньше аномалий, но тем больше блокировок и ниже параллелизм.

| Уровень | Грязное чтение | Неповторяющееся чтение | Фантомы |
| --- | --- | --- | --- |
| `READ UNCOMMITTED` | возможно | возможно | возможно |
| `READ COMMITTED` | нет | возможно | возможно |
| `REPEATABLE READ` | нет | нет | возможно* |
| `SERIALIZABLE` | нет | нет | нет |

\* В PostgreSQL `REPEATABLE READ` защищает и от фантомов, но стандарт этого не требует. `READ UNCOMMITTED` в PostgreSQL работает как `READ COMMITTED`.

- **Грязное чтение** — видно незафиксированные изменения другой транзакции.
- **Неповторяющееся чтение** — два одинаковых запроса внутри транзакции дают разные строки.
- **Фантом** — между запросами появились новые строки, подходящие под условие.

## CAP-теорема

В распределённой системе нельзя одновременно гарантировать все три свойства:

- **Consistency** — все узлы видят одни и те же данные;
- **Availability** — каждый запрос получает ответ;
- **Partition Tolerance** — система продолжает работать при потере связи между узлами.

На практике сеть может разделиться, поэтому выбирают между `CP` (жертвуем доступностью) и `AP` (жертвуем строгой согласованностью). Формулировка «выбери любые два» — упрощение: отказ от `P` означает отказ от распределённости.

## Реляционная модель

Реляционная база хранит данные в **таблицах** (отношениях):

- строка (запись, кортеж) — один объект;
- столбец (атрибут) — свойство объекта;
- связи между таблицами задаются ключами.

| Ключ / ограничение | Смысл |
| --- | --- |
| `PRIMARY KEY` | уникальный идентификатор строки, не `NULL` |
| `FOREIGN KEY` | ссылка на строку другой таблицы, обеспечивает ссылочную целостность |
| `UNIQUE` | значения в столбце не повторяются |
| `CHECK` | значение должно проходить условие |
| `NOT NULL` | значение обязательно |

Логическая модель описывает сущности и связи, физическая — таблицы, типы, индексы и размещение на диске.

## Нормальные формы

Нормализация уменьшает дублирование и аномалии при изменении данных.

- **1NF** — атомарные значения: в каждой ячейке одно значение, без списков и повторяющихся групп.
- **2NF** — 1NF плюс отсутствие частичной зависимости: неключевой столбец не зависит только от части составного ключа.
- **3NF** — 2NF плюс отсутствие транзитивной зависимости: неключевой столбец не зависит от другого неключевого столбца.
- **BCNF** — усиленная 3NF: любой определитель является потенциальным ключом.

Пример нарушения 3NF: в таблице `order (id, person_id, person_city)` город зависит от человека, а не от заказа. Город лучше хранить в `person`.

Денормализация (намеренное дублирование) иногда ускоряет чтение, но усложняет обновление данных.

## ER-модель

ER-модель (Entity–Relationship) описывает предметную область на логическом уровне:

- **сущность** — объект (`Student`, `Hobby`);
- **атрибут** — характеристика сущности (`name`, `age`);
- **связь** — отношение между сущностями (`Student — Hobby`);
- **кардинальность** — сколько объектов участвует в связи: `1:1`, `1:N`, `M:N`.

Связь «многие ко многим» в реляционной базе реализуют через промежуточную таблицу: `student_hobby (student_id, hobby_id)`.

## Реляционные и нереляционные БД

| Тип | Примеры | Хранение |
| --- | --- | --- |
| Реляционные (SQL) | PostgreSQL, MySQL, Oracle, SQL Server | таблицы со строгой схемой |
| Документные (NoSQL) | MongoDB | JSON-подобные документы |
| Ключ-значение | Redis | пары ключ → значение |
| Графовые | Neo4j | узлы и рёбра |

MongoDB — документная база, а не реляционная. PostgreSQL, MySQL и Oracle — реляционные.

## СУБД

**DBMS** (database management system, СУБД) — программа, которая управляет хранением, изменением и доступом к данным, а также транзакциями, блокировками, правами и резервными копиями. SQL — язык запросов, а не СУБД; SQL Server — конкретная СУБД.
