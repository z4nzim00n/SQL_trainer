# Теория Роли 2: рекурсия, массивы, представление

## Рекурсивный запрос по шагам

Идея: «маршрут это путь, который мы продлеваем на один город, пока не обойдём все».

```sql
WITH RECURSIVE tours AS (
    -- старт: первый шаг из города a
    SELECT point2 AS last_point, ARRAY[point1, point2] AS path, cost AS total_cost
    FROM nodes WHERE point1 = 'a'
    UNION ALL
    -- продление: из последнего города в ещё не посещённый
    SELECT nodes.point2, tours.path || nodes.point2, tours.total_cost + nodes.cost
    FROM tours
    JOIN nodes ON nodes.point1 = tours.last_point
    WHERE NOT nodes.point2 = ANY (tours.path)
)
SELECT ... FROM tours ...;
```

В каждой строке `tours` три вещи: где мы сейчас (`last_point`), как сюда пришли (`path`) и сколько это стоило (`total_cost`).

### Условие остановки

`WHERE NOT nodes.point2 = ANY (tours.path)`: не заходим в город, где уже были. Без него рекурсия будет ходить кругами бесконечно. Когда все города посещены, продлевать некуда, и рекурсия останавливается сама.

## Замыкание маршрута

В `tours` лежат пути, обошедшие все города, но ещё без возврата в `a`. Заключительный `SELECT` отбирает пути нужной длины и добавляет последнее ребро обратно в `a`:

- **длина**: `CARDINALITY(path)` равна числу городов; число городов считай запросом, а не вписывай (иначе пятый город сломает решение);
- **возврат**: соединяем с `nodes` по `point1 = last_point AND point2 = 'a'` и прибавляем стоимость этого ребра.

## Представление

`CREATE VIEW v_all_tours AS ...` сохраняет запрос под именем: напарник читает его как таблицу. Представление вычисляется заново при каждом обращении, поэтому оно подхватит новые данные в `nodes`.

Ключевые слова для примеров: `WITH`, `CTE`, `UNION ALL`, `ANY`, `CREATE VIEW`, `JOIN`.
