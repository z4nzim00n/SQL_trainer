# Общее ТЗ для тех, кто наполняет SQL-тренажёр

Проект: <корень репозитория> (статическая страница, SQL выполняется в браузере на PGlite = настоящий PostgreSQL). Прочитай СНАЧАЛА: <корень репозитория>/AUTHORING.md, затем образец задания tasks/day01/ex02_duplicates/ (все 6 файлов), tools/validate.mjs (как проверяется), js/checker.js (как сравнивается результат), data/pizza.sql (учебная база пиццерий: person, pizzeria, menu, person_visits, person_order) и data/demo.sql (мини-таблицы для примеров).

Пользователь: школьник School 21, новичок в SQL, говорит по-русски. Весь текст заданий на русском, обращение на «ты». Он предпочитает писать запросы БЕЗ псевдонимов таблиц (полные имена таблиц) и хочет понимать каждую строку. Поэтому в solution.sql и solution_commented.sql по возможности без псевдонимов, комментарии построчные, простым языком.

## Что создать для каждого задания (папка tasks/dayNN/exNN_короткое_имя/)
README.md (условие по тексту из ТЗ пользователя, в стиле образца: `# Задание NN. Название`, `**Разрешено:**`, `**Запрещено:**` при наличии, текст, пример вывода таблицей, если есть), theory.md, hints.md (три подсказки `## Идея`, `## Каркас` (с пропусками ______), `## Почти ответ`; готовое решение не раскрывать), solution.sql, solution_commented.sql, meta.json.
- theory.md: короткая, объясняет НОВЫЕ слова/приёмы задания, без готового решения. Примеры в ```sql-run выполняются на мини-таблицах demo (a, b, courses, students, products, sales; они автоматически показываются над примером; НЕ используй таблицы пиццерий в ```sql-run). Для новых слов добавляй такие примеры (2-4 штуки на тему). Если нужен пример именно на пиццериях, используй ```sql-pizza.
- meta.json: поля как в образце. title, dataset ("pizza"), ordered (true если в условии есть сортировка), forbidden/required (слова из «Запрещено»/«Обязательно»), positive (другие верные решения, должны проходить), negative (типичные ошибки, должны отклоняться; минимум 2, среди них обязательно «ответ, подогнанный под значения через VALUES», если задание возвращает таблицу из SELECT), для заданий с изменением БД поля setup и verify (см. AUTHORING.md). Название столбцов в результате должно совпадать с условием (используй те же имена, что в примере вывода).
- Если в задании два запроса («напиши два запроса»), решением является ОДИН итоговый запрос-ответ: делай задание с одним из способов в solution.sql, а второй способ добавь в positive; в README скажи, что в редакторе нужно решить любым из способов, а потом желательно переписать вторым (его проверяет positive).
- Задания, которые нельзя проверить результатом запроса или состоянием базы (например, «приведи скриншот»), делай максимально проверяемыми через verify, либо делай их «теоретическими»: если совсем нельзя, СКАЖИ об этом в отчёте и не создавай.
- Зависимости между заданиями (задание использует результат предыдущего: вставленные строки, представление, таблицу): каждое задание самостоятельное, нужное состояние создаётся в meta.setup (SQL предыдущих шагов, подставь эталонные решения).
- Скрытые данные: чтобы нельзя было «захардкодить» ответ, добавляй строки в ОТДЕЛЬНЫЙ файл data/pizza_alt_dayNN.sql (NN = твой день или «dayNN_dayMM»), идентификаторы строго в указанном тебе диапазоне (чтобы не столкнуться с другими авторами) и так, чтобы они не ломали решения. Не трогай data/pizza.sql и data/pizza_alt.sql.
- ВАЖНО для заданий про INSERT с «max+1»/подзапросом (day03): скрытые данные не должны мешать (ids >= 100 допустимы).

## Как работать и проверять
1. Рабочую копию проекта сделай: `cp -r <корень репозитория> ../work/<твоё_имя>` и там создавай задания, собирай `node tools/build.mjs`.
2. Проверка на настоящем PostgreSQL: `su postgres -c "createdb <твоё_имя>"` (один раз), затем `chmod -R a+rX ../work/<твоё_имя>; su postgres -c "cd ../work/<твоё_имя> && PGDATABASE=<твоё_имя> node tools/validate.mjs --verbose"`. Если PostgreSQL не запущен: `pg_ctlcluster 16 main start`. Валидатор проверяет: эталон проходит, positive проходят, negative отклоняются, примеры sql-run выполняются. Доводи до «Всё хорошо». Игнорируй ошибки sql-run в чужих/старых статьях docs/ если они остались (они не твои), но свои примеры должны проходить.
3. Когда всё зелёное, СКОПИРУЙ готовое в основной проект: свои папки tasks/dayNN/ (целиком), свой data/pizza_alt_*.sql, и только их. В основном проекте не запускай build и не правь чужие файлы.
4. Конкурентные запросы к одной базе не делай: у тебя своя база.

## Качество
Условия переписывай близко к тексту пользователя (можно поправить опечатки), но не меняй смысл. Подсказки должны реально вести к решению. Теория не должна раскрывать ответ. Названия папок: exNN_короткое_англ_имя (латиница, подчёркивания). Файл day.json в tasks/dayNN/ если его нет: {"title": "..."} (я напишу заголовок дня в твоём ТЗ).

В отчёте: что сделано (число заданий), что не получилось/сделано нестандартно, какие решения принял. Кратко.

## ДОПОЛНЕНИЯ (важно)
- Рабочую копию начинай с `rm -rf ../work/<имя>; cp -r <корень репозитория> ../work/<имя>` (старые копии в work/ устарели). Основной проект к этому моменту уже содержит: примеры `sql-run` на мини-таблицах demo (показываются над примером), `sql-pizza`, словарь терминов, ручные задания (`"manual": true`).
- ПРИМЕРЫ В ТЕОРИИ: ТОЛЬКО ```sql-run на demo-таблицах (a, b, courses, students, products, sales) или с самостоятельным созданием маленьких таблиц внутри самого примера (`CREATE TABLE ...; INSERT ...; SELECT ...;`: пример выполняется в откатываемой транзакции, показывается результат последнего запроса; но в этом случае таблицы над примером не покажутся, поэтому в тексте опиши, что в них). demo.sql не правь. Пример должен быть про одно новое слово и показывать эффект на крошечных таблицах (например, 2 таблицы и результат UNION).
- Слова-термины из твоих заданий: добавь словарь `docs/glossary_<имя>.json` в формате `{"ТЕРМИН": {"title": "...", "text": "1-3 предложения по-русски", "sql": "пример на demo-таблицах"}}` (ключ в ВЕРХНЕМ регистре; примеры не должны падать). В theory.md пиши такие слова в обратных кавычках, они станут кликабельными. Копируй свой glossary-файл в основной проект вместе с остальным.
- Идентификаторы в скрытых данных (data/pizza_alt_<имя>.sql) бери только из своего диапазона и ссылайся лишь на строки из pizza.sql / pizza_alt.sql / своего файла. Диапазоны: day00: 1000-1099, day01: 1100-1199, day02: 1200-1299, day03: 1300-1399, day04-05: 1400-1499, day06-07: 1500-1599, day09: 1600-1699. Подумай, чтобы скрытые строки меняли ответ (иначе ответ можно подогнать), но не ломали эталон.
- Ручные задания (две сессии psql, нельзя проверить в браузере): `"manual": true` в meta.json (подробнее в AUTHORING.md); решение (solution.sql) описывает шаги Session #1 / Session #2 и ожидаемый вывод в комментариях.
- Задания «напиши запрос, покажи EXPLAIN ANALYZE»: проверяй через verify состояние (индекс существует с нужным определением: pg_indexes.indexdef), а EXPLAIN объясни в теории и подсказках; в README скажи, что EXPLAIN надо выполнить кнопкой «Выполнить» самостоятельно.
- Ограничение вида «не используй прямые числовые значения для PK»: поставь в `forbidden` то, что реально можно поймать (например, слово VALUES), либо опиши правило в README и проверяй результат через verify; не придумывай хрупких проверок.
- Движок в браузере PGlite = настоящий PostgreSQL 16 (plpgsql, триггеры, представления, индексы, последовательности работают). Не используй расширения.
- Итоговый отчёт: максимум 12 строк.
